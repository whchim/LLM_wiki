# 项目定位与分层

> 状态：已定（项目对外定位的唯一声明）
> 版本：v0.1
> 日期：2026-09-11
> 适用：对外介绍、简历/面试表述、README 与文档索引的裁决依据
> **一句话**：这是一个**知识平台**（LLM Wiki 编译范式 + Google OKF），销售客户状态 Agent 是**建在它之上的第一个垂直落地应用**。

## 1. 为什么需要这份文档

项目在 Codex 迭代后形成两个能力面：通用的**知识编译与治理层**，以及面向销售场景的**状态事实链应用层**。两者共用同一套基础设施，若不在文档层面钉死层级关系，会出现三个具体问题：

1. **README 标题与简历/对外介绍不一致**——读者第一眼看到的定位与实际主体不符；
2. **文档索引失去裁决依据**——`WIKI-*` 族与 `SA-*` 族冲突时以谁为准没有规定；
3. **叙事重复**——同一套系统在简历中容易写成两段重复经历，而非"底座 → 落地"的递进。

因此本文件是**定位的唯一来源**：README 首段、文档索引中的"何时读"、对外介绍口径，均以本文件为准。

## 2. 两层结构

```text
┌──────────────────────────────────────────────────────────────┐
│ 应用层 · 销售客户状态 Agent（垂直落地）                        │
│   澄清会话 → evidence → state_proposals → 人工确认            │
│   → state_events（事实唯一写入口）→ current_states（投影）     │
│   敏感数值分层：正文占位符 + sensitive_numeric_values 受限表    │
└───────────────────────────┬──────────────────────────────────┘
                            │ 复用知识层的服务、认证、审计与数据地基
┌───────────────────────────▼──────────────────────────────────┐
│ 知识层 · LLM Wiki 知识平台（通用主体）                         │
│   编译（RAW → NEXUS）· 六维审核 · 混合检索 · 触发 watcher      │
│   OKF 对齐（Markdown + YAML Frontmatter）· 搜索缺口自增长      │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│ 共享基础设施 · FastAPI · JWT/RBAC · audit_logs · PG16+pgvector │
└──────────────────────────────────────────────────────────────┘
```

**层级判据**：一件事属于哪一层，看它**是否依赖具体业务语义**。

| 判据 | 知识层 | 应用层 |
|---|---|---|
| 是否假设业务对象 | 否，任何文档都能编译 | 是，只处理销售洽谈记录 |
| 权威存储 | 文件（Markdown + YAML Frontmatter） | PostgreSQL（事务 + 状态机约束 + 幂等键） |
| 谁定义需求 | `WIKI-00` PRD | `SA-01` 业务契约 |
| 复用关系 | 被应用层复用，不反向依赖应用层 | 依赖知识层与共享基础设施 |

## 3. 两层的权威与冲突规则

- **知识层需求**冲突时以 `docs/WIKI-00_LLM_Wiki_PRD.md` 为准，设计细节冲突以对应 `WIKI-*` 设计文档为准。
- **应用层需求**冲突时以 `docs/SA-01_销售客户状态Agent_业务契约.md` 为准。
- **跨层冲突**（应用层想改动知识层共享机制时）：先确认是否属于知识层通用能力——
  - 属通用能力 → 改知识层，并在 `WIKI-*` 记录动机；
  - 仅服务销售场景 → 留在应用层，**不得污染知识层通用逻辑**。
- **共享基础设施**（FastAPI 路由挂载、JWT/RBAC、审计、PG 连接与迁移）变更需同时评估两层影响，并跑全量测试。

## 4. 明确的事实边界（避免对外夸大）

| 事项 | 事实 |
|---|---|
| 项目性质 | 生产形态**原型**，不宣称已上线企业生产环境 |
| 知识库内容 | 企业业务内容已脱敏移除，现为**空骨架**（`init.sh` 可重建） |
| 应用层效果 | 只有 **synthetic 回放**（36 条）验证拦截率与契约通过率，**不得表述为真实业务准确率** |
| 检索指标 | `MRR@10`/`Recall@10` 来自**本地黄金集**（面试资产，不进公开仓库），不代表线上效果 |
| 规模数据 | 仓库内无用户规模/吞吐声明，相关数字属实习交付物的独立口径，不并入本项目 |

## 5. 对外表述口径

**一句话介绍**（对外统一使用）：

> 基于 LLM Wiki 编译范式与 Google OKF 规范的企业知识平台，将文档在入库时编译为结构化 Markdown 知识条目以替代向量 chunk；之上落地了一个销售客户状态 Agent，以事件溯源 + 人工门禁保证"AI 只提建议、事实由人确认"。

**分层表述**（介绍时先说什么）：

1. 先讲**知识层**：编译范式、OKF 对齐、混合检索与评测数字、质量门禁——这是项目主体与技术判断所在。
2. 再讲**应用层**：它证明底座能长出有状态机、有审计、有权限边界的真实业务应用。

**禁止的表述**：把应用层说成项目主体（会导致定位与 README 标题、文档族命名不一致）；把两层说成两个独立项目（会与"同一套基础设施"的事实矛盾）。
