# 销售事实澄清 Agent：传统基线

> 版本：v1 ｜ 阶段：2 ｜ 状态：已实现，等待负责人确认

## 1. 基线目的

在接入真实模型前，先回答一个基本问题：当前业务结果是否只需要表单和规则即可完成。基线与 Agent 共用状态集合和转移约束，但不写客户状态。

## 2. 结构化表单基线

销售手工填写客户需求、客户承诺、时间、下一步、证据备注和候选状态。缺任一核心字段即转人工。`field_count` 和固定 `operation_count` 用于衡量销售负担。

实现：`core/sales_baselines.py::run_structured_form_baseline`。

## 3. 关键词规则基线

规则基线在同一份自由文本中使用固定词典和状态短语：

- 识别 7 类有限事实类型；
- 记录命中短语的精确字符位置；
- 识别状态信号时遵守当前状态机；
- 缺少状态所需事实或出现否定表达时转人工；
- 不猜测同义表达，不生成追问，不调用 LLM。

实现：`core/sales_baselines.py::run_keyword_rule_baseline`。

## 4. 统一结果

两个基线都返回 `BaselineResult`：

| 字段 | 含义 |
|---|---|
| `baseline` | `structured_form` 或 `keyword_rules` |
| `accepted` | 是否足以形成候选建议，不代表事实已确认 |
| `proposed_state` | 通过状态机校验的候选状态 |
| `extracted_facts` | 规则或表单得到的事实 |
| `missing_fact_types` | 未补齐的关键事实类型 |
| `operation_count` | 用户需要完成的主要操作数 |
| `field_count` | 表单字段数或自由文本输入数 |
| `question_count` | 基线主动追问数，固定为 0 |
| `evidence_mode` | `manual_note` 或 `exact_span` |
| `notes` | 可解释失败原因 |

这使得后续 Agent 结果可以在同一案例上比较事实召回、证据忠实、操作负担和成本。

## 5. 公平性约束

1. 三个方案使用同一脱敏输入、同一状态机和同一人工标注；
2. 基线只能看到销售纪要，不获得人工标注答案；
3. `accepted` 只是“可形成候选建议”，负责人确认仍是事实写入前置条件；
4. 规则基线失败时转人工，不以错误猜测换取表面通过率；
5. 表单基线的较高字段数应计入销售操作负担，而不是隐藏在评测人员操作中。

## 6. 阶段 2 验收

- 表单和规则均可独立运行，不依赖 LLM、数据库或网络；
- 结果字段统一，可被同题回放脚本消费；
- 规则命中提供精确证据位置，否定表达不会直接形成事实；
- 非法状态转移和缺失最小事实会转人工；
- 测试覆盖完整表单、缺字段、状态边界、规则命中、规则缺口和否定表达。
