# 销售事实澄清 Agent 迭代计划

> 状态：阶段 5 已完成，等待负责人确认进入阶段 6  
> 前置成果：`SA-00` 至 `SA-05` 已完成销售客户状态受控工作流  
> 迭代原则：每完成一个阶段必须由负责人确认，未确认不得进入下一阶段

## 一、为什么启动本次迭代

现有系统已经具备状态机、幂等写入、敏感数值隔离、人工确认、审计、过期、撤回、更正和回放能力。这些能力构成生产控制面，但大部分可以由传统程序实现。

当前尚未证明 Agent 的增量价值：

- `sales_state_agent.py` 负责校验和接收 Agent JSON，并不负责完成真实模型调用；
- synthetic oracle 证明了契约和管道可重复，没有证明模型的语义理解质量；
- 当前流程没有基于信息缺口进行追问，也没有记录追问是否改变了状态判断；
- 尚未与结构化表单、关键词规则进行同题对比。

本次迭代不以“增加更多 AI 功能”为目标，而是验证一个可以被否证的命题：

> 面对混乱、不完整、包含主观表达的销售纪要，Agent 能否比结构化表单和关键词规则更低成本地形成可验证的业务事实，同时不降低状态写入的安全性。

## 二、产品边界

### 2.1 Agent 负责

1. 从脱敏销售纪要中区分客户明确表达、销售人员判断和未知信息；
2. 将可定位证据映射到有限业务本体；
3. 找出会影响客户状态判断的关键缺失事实；
4. 最多提出两个必要追问；
5. 收到补充回答后生成带证据的状态建议。

### 2.2 确定性程序负责

1. 输入校验、身份绑定、脱敏和敏感数值隔离；
2. 状态集合、状态转移和有效期约束；
3. 证据位置、输出 Schema 和权限校验；
4. 幂等、审计、成本记录、过期、撤回与更正；
5. 只有负责人确认后才能更新当前客户状态。

### 2.3 第一版不做

- Agent 自动确认客户状态；
- Agent 自主修改状态机或业务本体；
- 通用聊天助手；
- 语音识别、图片 OCR 和外部网页抓取；
- 根据 Agent 建议自动发送消息或执行外部操作；
- 宣称提升真实成交率或已经达到企业生产标准。

## 三、传统方案基线

在实现澄清 Agent 前，必须保留两个可运行基线。

### 3.1 结构化表单基线

销售人员手工填写：

- 客户当前进展；
- 客户明确表达；
- 下一步动作；
- 时间约束；
- 证据或备注；
- 建议状态。

它代表“完全不用 Agent，但把认知负担交给销售”的方案。

### 3.2 关键词规则基线

系统从同一份自由文本中用固定词典和正则识别有限信号，例如“同意试用”“进入报价”“合同已签”“暂缓”。无法确定时直接进入人工处理。

它代表“保留自由文本，但不使用 LLM”的方案。

### 3.3 公平比较要求

三个方案必须使用同一组案例、同一状态机和同一人工标注答案。Agent 不得获得基线不可见的客户结果信息。

## 四、核心数据对象

后续设计必须覆盖以下概念，最终字段以阶段 1 契约为准：

| 对象 | 含义 | 关键约束 |
|---|---|---|
| `FactClaim` | 从销售文本中提取的一条事实声明 | 必须标明主体、类型、来源和证据位置 |
| `ClaimAttribution` | 声明归属于客户原话、销售判断或外部事实 | 不允许把销售判断伪装为客户承诺 |
| `MissingFact` | 当前状态判断缺少的关键信息 | 必须说明为何会影响候选状态 |
| `ClarificationQuestion` | 针对缺失事实生成的追问 | 每轮最多 2 个，不得索取非必要敏感信息 |
| `ClarificationAnswer` | 销售对追问的补充回答 | 追加保存，不覆盖原始纪要 |
| `ClarificationSession` | 一次纪要从初始分析到形成建议的会话 | 有限轮次、可取消、可转人工 |
| `BaselineResult` | 表单、规则或 Agent 对同一案例的结果 | 用于同题评测，不进入客户事实投影 |

## 五、成功标准

第一阶段只使用高质量合成案例和人工标注，不冒充真实企业数据。真实试点指标单独记录。

### 5.1 工程门禁

- 100% 状态建议具有可定位证据；
- 100% 越权状态转移被确定性程序拦截；
- 100% 未经负责人确认的建议不能进入当前状态；
- 追问会话可重放，原始纪要和回答不可覆盖；
- 每次模型调用记录模型、Prompt、token、耗时和失败原因；
- 达到轮次或成本上限后必须转人工，不允许无限循环。

### 5.2 Agent 增量价值指标

| 指标 | 计算方式 | 第一版判断用途 |
|---|---|---|
| 关键事实召回率 | 提取命中的人工标注关键事实 / 全部关键事实 | 判断是否真正理解纪要 |
| 证据忠实率 | 能被原文或追加回答精确支持的声明 / 全部声明 | 控制幻觉和过度推断 |
| 状态建议修正率 | 被负责人修改或驳回的建议 / 全部建议 | 衡量负责人额外负担 |
| 追问有效率 | 回答后补齐关键事实的追问 / 全部已回答追问 | 证明追问不是装饰功能 |
| 无效追问率 | 重复、无关或已有答案的追问 / 全部追问 | 控制对销售的打扰 |
| 操作负担 | 字段数、追问数、处理时间 | 与结构化表单比较 |
| 单条成本 | 输入/输出 token、调用次数、估算费用 | 判断经济可行性 |

不能预设 Agent 一定胜出。若 Agent 在操作负担、事实质量和负责人修正率上不能形成综合优势，应保留传统方案或缩小 Agent 使用范围。

## 七、关键架构约束

1. Agent 输出不是事实，只是带证据的候选解释；
2. 原始纪要、追问和回答采用追加语义，不允许静默覆盖；
3. 本体和状态机由代码及版本化配置控制，模型不能自行扩展；
4. 模型失败不阻断传统流程，用户可以转结构化表单或人工处理；
5. 敏感数值仍使用受限表，默认不进入模型上下文；
6. 不用模型完成正则、权限、状态转移和数据库事务可以完成的工作；
7. 每个 Agent 决策都必须能还原输入、版本、证据、输出和最终人工决定。

## 八、阶段 0 结论

本次迭代的核心不是继续包装知识库或增加一个聊天入口，而是构造一个传统程序可以完成流程、但难以低成本完成语义澄清的业务环节。

如果最终对比表明 Agent 没有降低操作负担，或其事实质量不足以抵消成本和风险，项目应诚实保留传统基线，而不是为了“Agent”标签强行上线模型。
