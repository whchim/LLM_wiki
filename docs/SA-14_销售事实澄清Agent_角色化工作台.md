# 销售事实澄清 Agent：角色化工作台

> 阶段：5 ｜ 状态：已实现，等待负责人走通验收

## 1. 目的

工作台将销售录入、Agent 澄清和负责人确认拆开：销售只补充其能确认的事实；负责人查看结果和证据；状态变更仍由既有状态机和负责人决定接口执行。

## 2. 页面与权限

| 页面 | 普通用户 | 审核者 / 管理员 | 关键操作 |
|---|---|---|---|
| 销售澄清 | 仅自己的会话 | 可进入 | 提交脱敏纪要、回答实际追问 |
| 澄清审核 | 不可进入 | 全部会话 | 查看事实、归因、证据、缺口、成本与转人工状态 |
| 销售客户状态 | 不可进入 | 待确认建议 | 确认、修改或驳回建议，查看状态事件时间线 |

服务端不信任前端的提交人字段。`POST /clarifications/intake` 从 JWT 获取当前用户，并在幂等重放时先做访问校验，避免通过重用幂等键读取或改写他人记录。

## 3. 销售录入门禁

销售提交字段为客户脱敏标识、发生时间、来源、纪要正文与幂等标识。后端在写入前执行：

- 仅允许中文文本、受限来源枚举和带时区的发生时间；
- 拦截明显 Prompt injection、个人信息、密钥和内部标记；
- 金额、报价、预算、折扣和数量必须由受控加密器保存到独立数值表；当前部署未配置该加密器时，包含这类精确数值的纪要会被拒绝；
- 纪要正文只保存替换后的数值引用，供 Agent 使用的上下文不包含精确数值；
- 相同幂等标识返回既有会话，不重复创建证据。

## 4. 会话展示规则

- 每轮最多显示两个实际持久化的问题；回答只能提交给该轮真实问题 ID；
- 原纪要、Agent 输出和销售回答均为追加记录，页面没有覆盖或编辑入口；
- Agent 失败、契约失败、达到第二轮仍需追问时，页面展示“转人工审核”；
- 审核页展示事实、归因和精确证据位置，不将模型解释直接标为客户已确认事实；
- token 与耗时来自 `clarification_turns`，无调用记录时不展示虚构成本。

## 5. 人工验收路径

1. 用普通销售账号提交不含精确数值的脱敏纪要，确认创建会话且重复提交不增加证据；
2. 通过受控 `ModelPort` 执行方写入一轮 `needs_clarification` 输出，确认销售只能回答自己的问题；
3. 以审核者账号打开“澄清审核”，核对事实归因、引用、缺口、回答和成本；
4. 让会话达到轮次上限或注入一次契约失败，确认状态变为“转人工审核”；
5. 准备一个独立 `StateProposal`，确认负责人在“销售客户状态”查看中文状态和证据时间线后再决定。

## 6. 未完成项

当前工作台没有把真实模型供应商绑定到 `ModelPort`，也没有将澄清结果自动生成 `StateProposal`。这是刻意保留的边界：在模型质量、评测样本和负责人修正率未验证前，不应为了演示而连接自动状态写入。
