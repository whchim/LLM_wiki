# 领域建模

在设计过程中**主动**构建并打磨项目的领域模型。这是「主动」的纪律：质疑术语、编造边界用例、一有术语或决策结晶就立刻写成文档。（仅仅为了取词去读 `CONTEXT.md` 不算这个 skill：那是一个任何 skill 都能做的一行习惯。本 skill 用于**改变**模型的时候，而不只是消费它。）

## 文件结构

大多数仓库只有一个上下文（context）：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-事件溯源订单.md
│       └── 0002-写模型用-postgres.md
└── src/
```

如果仓库根存在 `CONTEXT-MAP.md`，说明有多个上下文，由地图指出每个上下文的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 全局决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 该上下文专属决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

**惰性创建文件**：只在有内容可写时才创建。若尚无 `CONTEXT.md`，在第一个术语敲定时创建。若尚无 `docs/adr/`，在第一个 ADR 需要时创建。

## 会话期间

### 对照术语表提出质疑

当用户用了与 `CONTEXT.md` 现有语言冲突的术语时，立即指出。例如：「你的术语表把『取消』定义为 X，但你这里似乎指的是 Y。到底是哪个？」

### 打磨含糊语言

当用户用了含糊或过载的术语时，提出一个精确的规范术语。例如：「你说『账号』：你指的是 Customer 还是 User？这俩不是一回事。」

### 讨论具体场景

讨论领域关系时，用具体场景做压力测试。编造能探到边界、逼用户把概念边界说精确的场景。

### 与代码交叉核对

当用户陈述某个机制的运作方式时，检查代码是否一致。发现矛盾就挑明：「你的代码是整单取消 Order，但你刚才说可以部分取消。哪个是对的？」

### 就地更新 CONTEXT.md

术语一经敲定，就地更新 `CONTEXT.md`。不要攒着批量写：要随敲随记。格式见 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

`CONTEXT.md` 必须完全不含实现细节。不要把它当规范、草稿纸或实现决策的仓库。它只是词汇表，仅此而已。

### 有节制地提出 ADR

只有以下三条**同时成立**时，才提议创建 ADR：

1. **难以回退**：日后改主意的代价可观
2. **缺少上下文会让人意外**：未来的读者会想「他们为什么这么做？」
3. **是真实权衡的结果**：确实存在备选项，你因特定理由选了其一

若三条缺其一，就跳过 ADR。格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)。

## 与项目文档体系的对接（LLM_wiki 适配）

本项目的权威文档是 `LLM_wiki_PRD.md`（需求唯一来源）与 `LLM_wiki_设计文档.md`（可直接编码的详细设计）。术语与决策的沉淀遵循以下原则，避免与现有体系冲突：

- **术语进词汇表**：领域术语敲定后写进 `CONTEXT.md`；若该术语已被 PRD/设计文档用作规范名词，则应在 `CONTEXT.md` 里与之保持一致并加说明。
- **重要决策进 changelog**：项目约定「重要变更记录到文档末尾 changelog」。凡够得上 ADR 三条规则的决策，在写入 `docs/adr/` 的同时，也应在对应 PRD/设计文档的 changelog 里登记一句。
- **PRD 为上**：若领域建模过程中发现术语或决策与 PRD 冲突，以 PRD 为准，并提示用户是否需修订 PRD。
- **语言**：所有术语定义、示例、决策记录正文使用中文（项目知识内容约定为中文）。
