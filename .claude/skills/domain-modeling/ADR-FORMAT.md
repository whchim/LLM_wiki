# 决策记录（ADR）格式

决策记录存放于 `docs/adr/`，使用顺序编号：`0001-短横线标题.md`、`0002-短横线标题.md`，以此类推。

**惰性创建** `docs/adr/` 目录：只在第一个 ADR 需要时创建。

## 模板

```md
# {决策的简短标题}

{1-3 句：当时是什么背景、我们决定了什么、为什么。}
```

就这样。一条 ADR 可以只是一段。价值在于记录**做出了**那个决定以及**为什么**，而不是填满各个小节。

## 可选小节

只有当它们确实带来价值时才纳入。多数 ADR 用不到。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：当决策会被重议时有用
- **Considered Options**（考虑的备选）：只有当被否掉的备选值得记住时
- **Consequences**（后果）：只有当存在不明显、需要指出的下游影响时

## 编号

扫描 `docs/adr/` 中现有最大编号，加一。

## 何时提议 ADR

以下三条**必须同时成立**：

1. **难以回退**：日后改主意的代价可观
2. **缺少上下文会让人意外**：未来的读者看代码会想「他们到底为什么这么做？」
3. **是真实权衡的结果**：确实存在备选，你因特定理由选了其一

如果一个决策容易回退，跳过：你反正会改回去。如果不让意外，没人会追问为什么。若没有真正的备选，除了「我们做了显然的事」外没什么可记的。

### 什么够格

- **架构形态**。「我们用 monorepo。」「写模型是事件溯源，读模型投影到 Postgres。」
- **上下文之间的集成模式**。「Ordering 与 Billing 通过领域事件通信，而非同步 HTTP。」
- **带锁定代价的技术选型**。数据库、消息总线、鉴权提供方、部署目标。不是每个库都记：只记那些要换得花一个季度的那种。
- **边界与范围决策**。「客户数据归 Customer 上下文所有；其他上下文只按 ID 引用。」那些明确的「不做 X」和「做 Y」同样有价值。
- **对显然路径的有意偏离**。「我们因 X 用手写 SQL 而不是 ORM。」任何合理读者会默认相反方向的做法都算。这能阻止下一位工程师「修好」一个原本就是有意为之的东西。
- **代码里看不到的约束**。「因合规要求我们不能用 AWS。」「因合作方 API 契约，响应必须低于 200ms。」
- **被否备选的否法定非显然时**。如果你权衡过 GraphQL 却因微妙理由选了 REST，记下来；否则半年后又会有人提议 GraphQL。
